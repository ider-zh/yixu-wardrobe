# 外部 Agent 热点穿搭生产 SOP

本 SOP 供衣序的外部内容生产 agent 使用。任务是检索当下的穿搭趋势，结合地区、天气、系统模特和情绪，制作生动九宫格写真，并通过项目内容与资源变更交付。后台负责资源 API、访问分析、用户穿搭观察、系统模特预览及 CDN 同步观察；不承担每日选题、图片创作或后台录入穿搭。

相关架构与实施顺序见[内容发布与 CDN 同步开发计划](content-publishing-plan.md)。项目操作规则见[AGENTS.md](../AGENTS.md)。

## 1. 交付范围与执行前提

- 每天交付一个发布批次。默认一个批次是一套完整穿搭的一张九宫格，即同一模特、同一服装的九个镜头，不是九套不同衣服；具体任务可指定批次内多套穿搭。
- 新内容只发布“生动”版，内部兼容标识为 `v2`。生产采用移交要求的两阶段流程：先制作私有“造型”九宫格锁定衣装，再结合模特参考照片生成“生动”九宫格。造型中间稿、实际提示词和生成记录留在私有工作区，不登记为公开 `v1`，不上传公共 CDN。
- 历史 `v1` 图片、资料和原编号保留归档，改造后的公开列表、详情、搜索、对比和资源索引不展示历史 `v1`。
- 首位模特使用 `female-01`，基础体为 [assets/model-bases/female-01.webp](../assets/model-bases/female-01.webp)。其中是正面、前侧、侧面、后侧、背面五视角，不能当作九宫格裁切。
- 外部 agent 交付最终 WebP、本地归档和内容清单，不直接填写 CDN 链接，不持有图床凭据，不操作用户私有数据。CDN 未配置、未就绪或同步失败时，前端直接使用项目图片的公开 URL；CDN 可用不是内容发布前置条件。
- 每次任务只执行当次生产与交付，不因本 SOP 自行创建定时任务、开通服务或修改服务器部署配置。

**当前入口：** 动态内容、仅生动展示、资源 API、项目图片 URL 与 CDN 队列已实现。内容结构见 `content/catalog.json`、`content/models.json`、`content/batches/*.json`，新批次必须符合 `content/batch.schema.json`。第 101 套、第二位模特和仅有 `v2` 的情况已纳入回归；不要更改冻结的旧 `catalog.js` 来添加新内容。真实图床尚未选定，CDN 未配置时使用项目图片，不阻塞发布。源码提交、服务器接收及网站可见仍需分别核验。

## 2. 开始一次生产任务

1. 检查工作区、当前分支和远程状态，读取项目最新规则，保留其他人的改动。已有未完成任务时先核对其批次标识，防止重复生产。
2. 以 `Asia/Shanghai` 确定目标发布日期。发布日期、天气适用日期与检索时间分别记录，不把今日查询的历史文章称作今日热点。
3. 查阅最近至少 7 个批次的主题、地区、服装轮廓、配色和情绪，避免连续重复同一方案。任务指定地区或模特时优先执行指定条件。
4. 检查可用模特及基础体版本。未指定时选 `female-01`；后续新增模特必须有登记资料与已批准的参考资产。
5. 读取 `content/batch.schema.json`、编号分配约定和部署环境的实际交付命令。下面的占位示例不能替代已实现的 schema；不因存在 SOP 就自行配置部署。
6. 有移交包时，在仓库外的私有目录解包，实际阅读 `HANDOFF.md`、`prompts/01-styling-template.txt`、`prompts/02-expressive-template.txt`，检查 `references/model-01.png` 等被引用文件能否打开。记录原始文件版本、实际使用的模特参考和模板改写。未找到文件时报告缺失并请求目录路径；不能声称已经读取或逐字复用了未提供的模板。ZIP、原始提示词、示例和参考 PNG 不复制到仓库或公开构建；下文只提炼通用制作规则。
7. 打开初始 100 套中与本次场景或材质接近的已验收生动图，至少查看整图与近景，核对细象牙色间隔、表情幅度、亲近的镜头互动及自然肤质。历史图只作为摄影与排版标准；模特身份、衣装和场景以本次已批准参考与策划为准。

## 3. 检索热点与地区天气

### 3.1 查找可核实的穿搭信号

以执行日为基准，优先查最近 7 天的街拍、服装轮廓、配色、材质、叠穿或地区生活场景；结果不足时扩展到最近 30 天，并明确标记时间范围。可以参考原始公开帖子、品牌或活动官方发布、时装报道，例如 [Vogue Fashion](https://www.vogue.com/fashion)。

每次至少整理三个候选选题，并用两个独立的具体原始来源交叉支持最终主题。转载同一篇文章不算两个独立信号。小红书、抖音等内容只在实际可访问和核实的范围内引用；无法访问、只有搜索摘要或没有发布日期时记录限制，换用可核实的来源，不编造榜单、互动数或排名。

检索词随日期和任务变化，例如“月份 + 城市 + 街拍”“最近一周 + 材质或轮廓 + 穿搭”“城市 + 活动 + 日期”。不能把预写的某个流行词永久当作当前热点，也不能直接把下一季秀场方案当作今天的当地穿着条件。

### 3.2 选择地区并核对天气

从候选主题中选择一个主要城市与实际场景。地区热度应有近期活动、当地街拍、官方文旅或其他可核实的公开信号；网站导航中的“热门城市”不能证明该城市近期走红。

通过[中国天气网](https://www.weather.com.cn/)或当地气象机构的具体城市预报页，核对目标拍摄或发布日期的天气：

- 城市及必要的城区，预报适用日期、发布或更新时间、查询时间。
- 最高与最低温、降水、风力；来源提供时再记录湿度或体感温度。
- 主要室内外活动、步行强度、昼夜温差，以及由此推导的叠穿、鞋履和防雨选择。

天气服务异常时更换可靠来源；仍无法核实时不编造温度，暂停依赖实时天气的正式选题。不能用多年平均气温替代当天预报。来源没有“体感温度”字段时，自己的穿衣判断必须标记为策划推断。

### 3.3 留下简短的选题依据

最终选择必须同时满足：有近期依据、适合该地区和天气、可以在九格中保持完整穿搭一致、与近期内容有区分。记录选择与放弃其他候选的原因，不把编辑判断写成客观热度排名。

对每个引用记录原始页面 URL、标题、作者或机构、发布时间、访问时间，以及一两句自己的概括。用于公开展示的清单只保存必要的事实与来源链接；完整调研过程、截图、下载内容和实际生成提示词留在私有工作区，不提交原文或外部图片作为项目素材。参考热点的是搭配元素，模特身份只来自项目批准的基础体。

## 4. 完成一份穿搭策划

生成前冻结一份简短策划，至少包含：

| 字段 | 要求 |
| --- | --- |
| 发布批次与目标日期 | 当天一个稳定批次标识并记录时区；同一任务重试不创建新批次 |
| 主题与地区 | 一个主题、一座主城市、一个可理解的活动场景 |
| 热点依据 | 至少两个独立具体来源及对应日期，不声称来源未证明的热度 |
| 天气依据 | 城市预报来源、适用日期、查询时间、温度与降水等实际字段 |
| 模特 | 登记编号、基础体路径、基础体 SHA-256 或版本 |
| 完整穿搭 | 上装、下装或连体服、外层、鞋、包和配件，注明颜色、材质、版型 |
| 天气适配 | 为什么该穿搭适合所选天气与场景；明确自己的策划推断 |
| 主情绪 | 一条自然情绪线，如周末相见的开心或散步中的好奇；不用九种冲突人设 |
| 镜头 | 为本套重新编排的九镜头微故事；逐格记录表情、动作、景别、鞋履可见性及与观者互动方式 |

一套穿搭在九格中保持同一件衣服、同一颜色与纹理、同一鞋包配饰。可调整姿态与景别，不在不同格中偷偷换衣、增减单品或改变模特身份。需要不同服装时建立另一套穿搭记录。

## 5. 生成标准化生动九宫格

### 5.1 模特参考与中性身份表述

提示词中的人物统一写为：

> 模特：以提供的模特参考照片为身份依据。九格均保持参考照片中模特的五官结构、发型发色、肤色、体态与身体比例一致；表情和动作随镜头变化。

实际调用时必须附上图片，不能只在提示词中写一个文件名。当前 `female-01` 对应 [五视角参考照片](../assets/model-bases/female-01.webp)，是身份参考，不是九宫格构图或固定站姿模板。移交包中的 `references/model-01.png` 使用前核对身份与登记参考；同一原图的 PNG 与 WebP 哈希不同，内容清单中的 `model_reference_sha256` 仍使用已登记 WebP 的哈希。

原模板还写死了特定脸型、五官、发色、发型、年龄与性别。适配其他模特时，将整段身份描述统一改为基于批准参考照片的中性表述，包括英文的人物指代；不能只替换一个称呼，却保留另一位模特的面部特征或身体比例。身份参考中的灰色基础服不属于目标衣装，生成时应完全替换。

### 5.2 两阶段生成与参考分工

1. **造型中间稿。** 读取 `prompts/01-styling-template.txt`，填入冻结的服装清单与具体场景，只提供批准的模特照片作为人物参考。生成 3 × 3 造型九宫格，覆盖正面、前侧、侧面、后背、坐姿及近景层次，至少五格展示完整衣装和鞋履。检查叠穿关系、颜色、材质、领口、扣具、裤裙长度、鞋包和配饰。中间稿重点验证衣装，不要求完成生动表情配额。衣装或身份有误时先修正中间稿。
2. **生动成片。** 读取 `prompts/02-expressive-template.txt`，按顺序提供模特参考照片与已验收造型图。前者控制人物身份，后者控制整套衣装与场景连续性；用本套重新设计的九镜头微故事替换静态展示镜头。不能只提供造型图而遗漏身份参考，也不能将造型图的无表情站姿直接复刻九次。生动阶段的含鞋履门槛为三格，同时增加亲近的中景、近景和至少一个自然动态瞬间。
3. **核对参考是否实际送入工具。** 记录两张参考图的输入次序与用途；遇到参考图数量、格式或工具能力限制，先解决输入条件，不悄悄降级为纯文字生图。工具不支持原始模板某个参数时如实记录调整。
4. **保存生产证据。** 本次填写后的两份最终提示词、实际参考、造型中间稿、生动母本及验收记录保留在私有工作区，不进入 Git、公开静态包或公共 CDN。

已核对的移交包还包含以下可用材料；文件均保留在私有目录，公开 SOP 不收录其完整提示词或 PNG：

| 包内文件 | 用途 |
| --- | --- |
| `prompts/100-styling-example.txt` | 检查一套精确衣装如何描述层叠、扣合、长度与不新增配件；不复制为每日固定穿搭 |
| `prompts/100-expressive-example.txt` | 检查九镜头微故事如何逐条落实表情、动作和景别；每套重写 |
| `references/look-100-styling.png` | 对照造型中间稿的衣装锁定效果；仅在任务明确复现第 100 套时作为该套衣装输入 |
| `examples/look-100-expressive.png` | 对照象牙色分隔、表情幅度与互动节奏；只看图验收，不作为第三张生成参考图 |

以下为对已读取模板提炼的**通用提示词骨架**，不是原模板全文。实际使用时先阅读私有原模板并做中性化适配，再将相同约束完整合入；不能只输入“按 SOP 生成”或留着占位符执行。

### 5.3 九宫格排版与摄影细节

- 最终是一张静态、完整的 3 × 3 九宫格，从左到右、从上到下对应清单的 01—09。每格只出现参考照片中同一模特，不增加其他人物。
- 整张画布使用 2:3 竖幅，兼容现有 1024 × 1536 资产；生成工具支持时可用更高原生分辨率，不拉伸、压扁或裁掉鞋履与头部来凑尺寸。
- **九格之间必须有连续、细窄的象牙色留白分隔。** 两条竖线和两条横线贯通，行列对齐；不能无缝接图、用场景中的柱子充当分隔、改成不等大拼贴或加标题区。以初始 100 套及移交成品示例的观感为基准；本 SOP 建议 1024 像素宽时线宽约 4—8 像素，默认约 6 像素，高分辨率等比缩放。原模板只要求细象牙色间隔，没有给出像素值；这些数值是制作建议。
- 分隔嵌在画布三等分边界附近，不在九格之外另外插入间距扩大画布，不给每格重复加粗外框。裁切仍按 `floor(W × col / 3)`、`floor(H × row / 3)` 等分，最后一列和最后一行到图像边缘。逐格预览时应只带窄分隔边，不混入相邻人物或切断关键衣装。
- 使用明确一致的拍摄光线、色温、空间材质与适度景深；肤质、发丝和衣料纹理自然。保持本次天气与场景的真实氛围，不把全部主题强行改成相同色调。
- 镜头与观者建立亲近的关系，动作有重心、衣物有自然动态。保留完整头部、自然头肩比例、合理的手脚与遮挡；近景表情可辨，全身与中全身镜头的鞋履完整可见。
- 服装细节写清从外到内的叠穿顺序、扣合状态、领口袖口与下摆长度，并列出不新增的配饰；仅写“高级、复杂、时尚”不足以固定穿搭。包可按动作自然换位置或放在椅边，同一套的设计、颜色、材质、肩带与扣具保持一致。照片中始终完整着装、衣料不透明，不出现画外同伴的手或遮脸道具。
- 图片内不生成文字、镜头编号、品牌水印或虚构标志；镜头名称和说明保存在清单中。

### 5.4 每套重新设计九镜头微故事

先写一条主情绪线，例如相约逛展时从认出对方到边聊边笑，再为九格分别写表情、动作、景别和互动。交付前核对以下**硬性门槛**：

- 至少 **5 种明显不同的表情**，包含露齿笑与张口大笑；仅改变笑容幅度、歪头方向或复制同一个微笑不算多种表情。
- 至少 **6 种不同动作**，例如走动、坐下、回身、邀请、倚靠和回应场景物件；只换站立方向不算六种动作。
- 至少 **3 格包含完整鞋履的全身或中全身**，看得清整套衣装与比例；建议穿插全身、中景和近景，不把整行做成相同站姿的正侧背展示。
- 至少 **5 格与观者有目光或友好手势互动**；一直看向远处、低头或背对镜头不能充数。
- 每套重新设计脚本与场景中的具体动作，避免批次之间反复照搬同一九格顺序。表情和手势需自然、服从同一段情绪线，保持衣装和模特身份稳定。

## 6. 验收与 WebP 转码

造型中间稿先核对至少五格完整衣装与鞋履，再验收生动图。先检查整张，再按等分坐标逐格打开检查，同时对照模特参考、已验收造型图和一张初始生动图的摄影/排版标准。逐格填写私有验收表：镜头编号、实际表情类别、动作类别、景别、鞋履是否完整、是否与观者互动、身份/衣装/手部是否通过；再汇总是否达到 5 种表情、6 种动作、3 格含鞋履全身或中全身、5 格互动。不能只检查提示词或清单中是否写了这些词。

分别验收整图 2:3、严格九个等大画面、两横两竖的细象牙色分隔连续可见，且九格等分预览正确。缺少分隔、缺格、多人物、衣装突变、表情或动作未达门槛、明显畸形、缺失鞋履、裁断头部或文字乱码均不能交付。文件签名、尺寸和哈希通过只证明资源完整，不证明这些视觉要求已经满足；必须实际看图。

局部失败优先修复失败镜头，修复后重新检查与其他八格的一致性；不能用其他模特、历史图片或复制某一格凑数。实际画面偏离原策划时，修图或如实更新镜头说明，不保留与画面不符的文字。

验收后的唯一生成母本转码为单帧有损 WebP，建议 `quality=85`、`method=6`，不经过 JPG 中转，不重复有损编码。使用可用的确定性图像编码工具进行转码，例如：

```sh
cwebp -q 85 -m 6 -metadata none input.png -o output.webp
```

`input.png` 与 `output.webp` 是工作区示例文件名，不是必须存在的项目脚本。参数依据 [cwebp 官方文档](https://developers.google.com/speed/webp/docs/cwebp)；工具或版本不同可能导致输出字节不同，不能假定哈希一致。

最终文件必须实际解码为 WebP，尺寸和方向正确，九宫格画幅完整。当前静态资源检查只支持 RIFF + 单个 VP8 块的简单有损 WebP，交付时应使用兼容输出；不能直接套用个人试穿成品带 XMP 的编码配置。重新打开编码结果检查脸部、头发、纹理及象牙色分隔边缘，确认压缩后间隔仍清晰，再记录真实尺寸、字节数与最终文件 SHA-256。本地保留最终生动 WebP；造型中间稿、生成母本与最终提示词私有保留，不进入 Git。

## 8. 验证 提交 与服务端接棒

完成清单和资源更新后，运行以下必需检查；它们会读取新批次，不需要改写检查脚本或旧数据：

```sh
node scripts/check.mjs
node qa/regression-expressive.mjs
node scripts/build.mjs
node qa/regression-content.mjs
git diff --check
```

检查应覆盖图片签名、尺寸、SHA-256、九格索引、模特与穿搭引用、批次唯一性、`v2` 展示范围、旧编号与收藏不变。涉及交互或布局时增加相应浏览器回归。查阅 Git 的实际差异，确认只包含内容元数据、最终公开 WebP 和必要项目变更，没有原始生成文件、完整提示词、用户照片、私人调研记录或凭据。

遵守项目现有 Git 授权提交与推送，核对远程 SHA 与 CI。只在配置好的交付链路内更新服务端；普通源码推送和 CI 不自动构成部署授权，也不证明服务端已收到内容。

已启用本地提交观察器的环境会在工作区干净且提交变更后执行受控交付；没有启用时按 [部署说明](../deploy/README.md) 显式执行交付。发布后至少核对 `/api/content/home` 的首屏编号、页面快照与 API 的 `revision`、首屏图片实际字节及哈希，并检查后台网站交付状态。只检查总套数或 CI 无法发现“新图存在但首页未更新”。不要让内容 agent 自行重启无关进程或配置公共生产环境。

目标服务端流程是：接收已授权的代码与资源版本 → 验证清单 → 将公开 WebP 归档并准备项目图片公开 URL → 切换可见内容版本，以项目图片 URL 展示 → 后台按哈希增量同步 CDN → 核实远端可访问及资源元数据 → 逐图优先使用已验证的 CDN 链接。外部 agent 不代替服务端直传图床；同步失败时继续展示项目图片，通过后台观察和重试，不重新生图。归档和项目图片 URL 未就绪的批次继续保留旧可见版本，不能用缺图版本替换。

前端始终保留服务端返回的项目图片 URL 作为后备；CDN 加载失败时单次回退，不循环重试。公开 URL 是受控公开资源路径，例如 `/assets/looks/YYYY-MM-DD/look-ID-female-01-v2-r1.webp`，不能是本机路径、私有归档路径或用户照片接口。

## 9. 最终交付报告

交付必须列出：发布日期与批次、地区和天气适用日期、主题与来源链接、模特编号、穿搭编号、WebP 相对路径、尺寸/字节数/SHA-256、两阶段参考使用情况、细象牙色分隔验收、实际表情/动作/含鞋履全身或中全身/互动数量、身份与衣装/手部/九格结构验收结果、提交 SHA、CI 链接，以及服务端接收、项目图片 URL 可用、CDN 同步、前端可见状态的实际证据。报告可给出简短的验收结论；不公开当次完整提示词、私有参考路径或中间稿。CDN 尚未配置时可报告“项目图片已展示，CDN 未配置”，不因此将内容记为发布失败。不能观察到的状态写“未核验”，不能用 CI 成功替代资源或网站验收。

完成标准是当次内容与资源通过验证，按授权推送，并如实交接其后状态；已配置交付链路时，再核对本次批次的服务端接收、项目图片 URL、前端可见以及独立的 CDN 同步状态。CDN 验证通过后再报告使用 CDN。仅推送源码而尚未交付服务器时报告“源码已更新，线上未核验”，不能报告“已上线”。

### 电商摄影图组标准（2026-11-13 调研后更新）

本节是衣序自有设计展示站的制作标准，不是 Amazon、淘宝或天猫的上架合规证明。此次三位 agent 分别核验平台规范、摄影设计、工具与技能，并交叉评审；当前三张样板干净、轮廓清楚，但每件只有一个图片资产，网页的局部放大也复用了主图。下一版应增加有信息分工的镜头，而不是把同一物件放进更多装饰背景。

#### 1. 先写参考证据表

每件任务先记录以下三类信息，保存在私有制作记录中：原写真实际可见的结构；已登记 AI 单品母图中已经批准的设计；没有可靠参考的未知部位。已登记 r1 是本设计的视觉基线，不证明真实商品存在，也不证明原写真未展示的结构。完整色型锁定使用单品母图，原写真只约束其中实际可见部分。

针织衫在第 102 套中被外套与裙腰遮住，不能从原写真验证完整衣长、后背和衣摆；长靴的鞋底与细缝也缺乏充分参考。裙装的腰头、前中缝、A 字轮廓与裙长较清晰，因此优先用皮裙试制。需要真实成分、工艺、内里、扣件或背面结构时，必须补对应高质量参考；缺失时省略该镜头，或明确作为待批准的设计补充，不能编造为产品事实。

#### 2. 每件先规划四个角色

| 角色 | 回答的问题 | 拍摄与生成约定 |
| --- | --- | --- |
| 完整识别图 | 单品是什么，整体颜色与轮廓如何 | 全件入镜，适度留白，明确承托或物理合理的呈现；依据材质控制阴影与高光。 |
| 结构说明图 | 哪个已知结构值得看清 | 围绕领口、腰头、中缝、鞋头或鞋跟独立取景，保留母图结构，不添加未知五金或接缝。 |
| 肌理与形态图 | 面料或表面如何接光、垂坠 | 使用侧向柔光与自然折面展示设计效果；新生成纹理属于 AI 设计演绎，不能当真实材质的检测或工艺证据。 |
| 穿着上下文 | 与模特、其他单品的比例关系如何 | 优先引用已验收写真中的对应画面；新生成穿着图须同时参考登记模特照片、单品母图与原穿搭，重新验收身份与服装。 |

每张镜头必须写明新增信息。裁切旧图可标为“主图局部”，裁切原九宫格可标为“原写真穿着参考”；两者不能标成新取景或高分辨率微距。一个四图组可以诚实复用一张原写真，但前三张不能只是相同主图换裁切、换背景。

#### 3. 三类服饰的镜头配方

| 单品 | 完整识别 | 结构说明 | 肌理与形态 | 穿着上下文 |
| --- | --- | --- | --- | --- |
| 针织 | 袖子自然弯折的完整平铺，左上大柔光与弱填充 | 领口、肩部斜向近景，核对圆领与罗纹 | 已批准的袖口搭在身片上，柔侧光表达针织起伏 | 第 102 套第 5 格；只解释已见的蓝色叠穿，不补造背面 |

针织避免过度磨皮和粗大编织纹；皮裙避免漆皮般镜面高光与无重力的均匀悬浮影；深色长靴保留鞋头、鞋跟与鞋底边缘的层次，不用整体提亮改变颜色。道具只承担支撑或场景解释，不遮住产品，不让三件都复制相同居中悬浮构图。

#### 4. 分开执行两条流程

**基底场景编辑**：把已批准母图明确标为编辑目标，限定背景、留白、承托、光照或阴影的修改范围。输出仍须与母图并排核对，不能因工具声称保留产品就跳过验收。此路线不能制造未见结构或新视角。

**参考约束的新取景**：把母图、原写真及必要局部参考分别注明用途，逐张生成指定镜头。它会重新解释像素，须重点核对色型、领口、罗纹、拼缝、腰头、鞋头和鞋跟。每轮只调整一个主要问题；不能把服饰轮廓的漂移当成摄影风格变化。

通用任务单应包含：目标渠道、镜头角色、要回答的视觉问题、各参考的用途与可见范围、不可变结构、构图、光线与支撑、允许变化、未知部位处理、输出标签、逐项验收结果。通用提示词可用占位结构公开；当次填好的完整提示词及生成母本继续私有保存。

#### 5. 实际验收

建议内部评分：单品一致性 35 分，光线与材质表达 20 分，镜头信息增量 15 分，物理与空间可信度 15 分，清晰度与交付 10 分，衣序视觉统一 5 分。总分至少 85，且一致性至少 30/35；这是本项目的设计验收建议，不是平台或工具认证。

逐图与母图并排检查颜色、轮廓、结构和比例，按 100% 实际像素查看边缘、接缝、重复纹理和压缩块。出现明显改色改型、错误接缝、未知结构冒充既有事实、严重漂浮、穿插或伪造品牌时直接退回，总分不能抵消。不把插值锐化当作新增真实细节，不用生成纹理证明材质成分。

#### 6. 当前清单与交付边界

`content/products.json` 使用 `asset` 登记完整主图，可选 `gallery` 登记最多八张独立设计细节图；每项使用 `title`、`caption`、`asset`，资源格式与主图一致。Node/Python 导入、静态导出和资源 API 均校验并提供画廊，前端按登记顺序显示缩略图和独立细节特辑。第 102 套棕裙已完成主图、腰头与裙摆的首轮验收，可作为交付样板；原写真通过 `appearances` 保留穿着上下文。新一轮仍先私有试制并验收，不把待审草稿放入公开目录。

`gallery` 只用于独立设计细节图；完整图放在 `asset`，原写真穿着参考使用精确 `appearances`。不把主图裁切冒充独立近景，不把生成细节写成实物工艺证明。沿用最终 WebP、本地保存、SHA-256、CDN 未就绪时使用项目 URL 的交付方式。新图使用新修订和资源 ID，不覆盖已发布 r1 字节。

#### 7. 调研来源与工具选择

访问日期为 2026-11-13；平台规则和工具能力在实际执行时复核。

- [Amazon 商品图片要求](https://sellercentral.amazon.com/gp/help/external/G1881?language=en_US)：美国站 MAIN 有白底、完整主体及成人服装/鞋履等品类要求；官方页搜索索引可读，直开需要 JavaScript。不得据此断言所有平台、所有图片必须用同一种构图。

- [Pebblely 操作指南](https://pebblely.com/how-to/)：已核实场景、风格参考和输出比例选项；当前可用 API 与服装专属能力未在本次证实。
- [阿里妈妈万相营造](https://agi.alimama.com/)：官方索引列出智能商详、百变背景等能力；直开正文不可读。本次未核验其套餐、API、实际效果，也未取得淘宝/天猫现行完整类目图片规范。
- [amazon-product-photography 技能源码](https://github.com/nexscope-ai/Amazon-Skills/blob/main/amazon-product-photography/SKILL.md)：可参考逐图规划和输入证据分层，但附带服务推广指令，不整体安装。其他高安装量同名技能存在额外服务登录、通用提示词或来源不可核验等问题，不以安装量代替内容审查。
